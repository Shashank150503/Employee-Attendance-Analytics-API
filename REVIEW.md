# REVIEW.md

Defects found in the starter `app/main.py` (line numbers refer to the starter as delivered).

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes`, l.35 | `punch_in.replace(hour, minute)` builds the shift start in the **same zone as the punch** (UTC from Mongo, or the server's local zone), not IST. Shift 09:30 IST is treated as 09:30 UTC, so everybody is ~5.5 h "late" or the sign is wrong. | Punch in at 09:35 IST: stored lateness is hundreds of minutes. | Shift start is built as an explicit IST datetime for the attendance date (`_at()`), then compared as aware datetimes. |
| 2 | `compute_late_minutes`, l.36-37 | Floors **then** compares `> 10`, so 09:40:01-09:40:59 (floor = 10) is not late. R2 says strictly more than 10:00 *in seconds*. `int(x/60)` also truncates toward zero for early punches. | 09:40:01 on a 09:30 shift returns 0, spec says 10. | Compare whole seconds to 600 first (`seconds > GRACE_SECONDS`), then floor-divide by 60. |

**Looked at and decided it is not a defect**

* `load_dotenv()` with no `override`: it does not override real environment variables, which is what the contract asks for.
* `IST = timezone(timedelta(hours=5, minutes=30))`: correct and safe, because India has no DST.
* `doc.pop("_id")` after `insert_one`: removes `_id` from the response, which is right in intent. It was the extra `id` field and the other leaks that were wrong.
* Using `def` (not `async def`) endpoints with blocking PyMongo: correct, FastAPI runs them in a threadpool, so the event loop is not blocked.
